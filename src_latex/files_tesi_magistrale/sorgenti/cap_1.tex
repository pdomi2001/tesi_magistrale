\chapter{Introduzione}

\section{Scopo del progetto}
Il progetto si propone l'obiettivo di verificare la possibilit\'a di utilizzare le peculiarit\'a del linguaggio erlang\cite{web:erlang} o elixir\cite{web:elixir} per migliorare la gestione dei trasferimenti dei dati nella somministrazione di test.

Nello specifico se sia possibile migliorare e rendere pi\'u robusto ed affidabile il trasferimento dei dati dalle postazioni degli studenti al server che si occupa di raccogliere ed elaborare i risultati.

I problemi principali che ci proponiamo di risolvere sono l'affidabilit\'a nel trasferimento dei dati a causa di problemi di connettivit\'a e la garanzia di congruenza dei dati stessi.

Per fare questo si vuole creare una rete di nodi (da stabilire) che permettano alle postazioni studente di inviare sia le versioni temporanee che quelle definitive delle risposte al test, ai server che raccolgono i risultati e realizzare anche, sempre tramite la rete di nodi erlang una rete affidabile e resistente ai problemi.

\section{Introduzione al problema}
Al momento la somministrazione dei test al PC utilizzando i browser web utilizzano una architettura di tipo Client/Server per gestire la comunicazione tra il server che gestisce e distribuisce il test e i vari client che registrano ed inviano le risposte inserite dagli studenti.

In linea di massima lo schema \'e quello visibile in figura \ref{fig:configurazione_attuale}.

In questa modalit\'a ogni client fa una serie di chiamate al server web che genera dinamicamente la pagina da visualizzare sul browser del client.
Questa pagina viene generata diversamente in base allo stato in cui si trova il client. Ad esempio potrebbe essere la pagina per fare il login alla piattaforma oppure quella in cui si inseriscono i propri dati passando per le pagine in cui ci sono le domande del test con i campi in cui l'utente inserisce la risposta esatta fino ad arrivare alla pagina con il punteggio realizzato del test.

Tutte queste interazioni avvengono, attraverso chiamate http o https e sfruttano direttamente le risorse della macchina su cui \'e installato il web server.

All'aumentare del numero di utenti che si collegano aumenta anche la quantit\'a di risorse che vengono utilizzate fino ad arrivare ad un punto, dipendente dall'architettura e dalle risorse presenti sulla macchina che impedisce al web server di funzionare correttamente provocando una serie di errori.


\section{Possibili soluzioni}

\subsection{Aumento delle risorse}
La prima soluzione e quella pi\'u comune \'e quella di aumentare le risorse disponibili per il web server.

Questo si pu\'o fare acquistando nuovo hardware e installando sulla nuova macchina un nuovo web server che per\'o va configurato ed ottimizzato correttamente e richiede un investimento periodico, oltre che economico per l'acquisto dell'hardware, anche di tempo per l'installazione, la configurazione e il trasferimento dei dati tra una macchina e l'altra.

\subsection{Allocazione dinamica delle risorse}
Un'altra soluzione pu\'o esser quella di installare il nostro web server, fin dal primo momento, in un sistema che permetta una scalabilit\'a delle risorse dinamica senza essere legati direttamente all'hardware presente.

Un primo livello \'e creare una server farm interna all'azienda che permetta la gestione delle macchine in ambiente virtuale. In questo caso lo sfruttamento delle risorse viene gestito e diviso, tra le risorse disponibili, da una infrastruttura di base che nasconde il vero hardware.

Un secondo livello \'e quello di affidarsi a sistemi distribuiti a livello geografico come Amazon AWS, Microsoft Azure, ecc. che permettono anche di allocare dinamicamente le risorse in base al carico di lavoro che \'e in quel momento presente sul nostro sistema.

In questi casi l'investimento dal punto di vista temporale, rispetto al caso precedente, viene quasi annullato dato che \'e sufficiente, per aumentare le risorse cambiare qualche parametro anche a macchine accese, per assegnare le risorse necessarie a sostenere il carico di lavoro che si presenta.

D'altro canto l'investimento economico in questi ultimi due casi \'e necessariamente pi\'u grande di quello richiesto dal primo caso di cui abbiamo parlato.

\subsection{Un nuovo approccio}
Il lavoro che verr\'a portato avanti in questa tesi si pone come obiettivo quello di trovare un sistema per evitare il problema del sovraccarico del server web da parte di troppe connessioni contemporanee senza dover investire in nuove risorse hardware.

Per far questo creeremo in layer intermedio tra il web server e i client come in Figura \ref{fig:nuova_configurazione}.

\begin{figure}[!hbtp]
	\includegraphics[width=0.5\textwidth]{figure/Disegno_002_Configurazione_desiderata.png}
	\caption{Nuova configurazione}
	\label{fig:nuova_configurazione}
\end{figure}

Questo nuovo layer deve occuparsi, usando dei messaggi, di fare da tramite tra i client e il server web gestendo le richieste in modo che non ne arrivino troppe contemporaneamente al web server.

Sfortunatamente questo richieder\'a anche di cambiare il modo in cui i client e il server comunicano tra di loro.

In particolare non sar\'a pi\'u direttamente il server a generare la pagina da visualizzare sul client ma passeremo ad una gestione pi\'u dinamica della creazione delle pagine direttamente sul client in javascript con un approccio di tipo Client Side Rendering o meglio ancora DOM Manipulation.

Questo approccio richiede che il client abbia un browser pi\'u moderno dato che una parte del processo viene spostata lato client. D'altro canto ormai tantissime applicazioni, come ad esempio Google mail o Facebook, hanno questo tipo di approccio.

Gli scambi tra il client, il gestore di messaggi e il server PHP, avverranno quindi solo tramite messaggi codificati in JSON e non come pagine web intere. Questo ci permetter\'a, in ottica futura, di poter modificare una singola parte (client, server o gestore di messaggi) senza dover modificare obbligatoriamente le altre.
