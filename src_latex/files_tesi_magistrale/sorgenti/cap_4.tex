\chapter{Implementazione della comunicazione}
Per l'implementazione del gestore di messaggi ci affideremo al web server implementato in Erlang \cite{web:erlang},  Yaws \cite{web:yaws}. 

Yaws usa un sistema simile a quello di PHP.
Permette infatti di includere codice erlang direttamente all'interno della pagina WEB inserendolo all'interno delle coppia di tag <erl> e </erl>.

La comunicazione tra client e server avviene tramite il passaggio di messaggi attraverso il gestore dei messaggi in erlang.

Questa si compone di due fasi distinte: la comunicazione tra il client e il gestore di messaggi e la comunicazione tra il gestore di messaggi e il server vero e proprio.

Nella prima il client comunicher\`a con il gestore del messaggi attraverso semplici connessioni http o https in get o post che verranno processate dall'interprete erlang in Yaws.

Nella seconda fase il gestore di messaggi, comunicher\`a con web server PHP. Per evitare che si ripresenti lo stesso problema che avevamo con troppi client implementeremo una procedura che permetta solo un numero massimo di connessioni contemporanee. Sar\`a il gestore dei messaggi a permettere a tutti i client di collegarsi contemporaneamente e ad inviare i messaggi ricevuti al server al ritmo che il server accetta.

\section{Comunicazione tra client e gestore dei messaggi}
\subsection{Lato client Javascript}
Visto che il client gira su un browser la comunicazioni verr\`a gestita tramite codice Javascript. La comunicazione avverr\`a usando REST.

Utilizziamo per questo come base per la comunicazione alcune funzioni javascript:
\begin{verbatim}
let cache = {};
const request = (url, params = {}, method = "GET", customHeaders = {}) => {
    let cacheKey = JSON.stringify({ url, params, method });
    if (cache[cacheKey]) {
        return cache[cacheKey];
    }
    
    // Definiamo le opzioni base inclusi gli headers
    let options = {
        method,
        headers: {
            "Content-Type": "application/json", // Default per API moderne
            ...customHeaders
        }
    };  if ("GET" === method) {
        url += "?" + new URLSearchParams(params).toString();
    } else {
        options.body = JSON.stringify(params);
    }
    
    const result = fetch(url, options).then((response) => response.json());
    cache[cacheKey] = result;
    
    return result;
};
const get = (url, params, headers) => request(url, params, "GET", headers);
const post = (url, params, headers) => request(url, params, "POST", headers);

\end{verbatim}

per passare i parametri al gestore dei messaggi metteremo i valori in un array

\begin{verbatim}
const dati = 
{ 
    "msg_type": "test_messaggio", 
    "contenuto": "Contenuto messaggio" 
};
\end{verbatim}
e poi li convertiremo in json
\begin{verbatim}
const json = JSON.stringify(dati);
\end{verbatim}
infine invocheremo la funzione per inviare i dati e leggere il risultato della elaborazione
\begin{verbatim}
post("server.yaws", json, headers).then((post_res) => {
        const result_type = post_res.risposta.result_type;
        const risposta = post_res.risposta.result;
    }); 
\end{verbatim}
Il contenuto di risultato dipender\`a logicamente dal comando che avremo inviato pur avendo la struttura di base che abbiamo definito nel capitolo 3.

\section{Lato gestore dei messaggi}
Dal lato del gestore dei messaggi dovremo gestire le richieste fatte in json ed analizzare i dati che ci verranno inviati.
Nel server Yaws la funzione che viene eseguita per prima \`e la funzione out().

\begin{verbatim}
out(Arg) ->
    Method = method(Arg),
    Risultato = try
      processa_comandi(Method, Arg)
    catch
      _ -> json:encode(#{
        <<"title">> => <<"Arrivato messaggio in POST">>,
        <<"method">> => <<"POST">>
    })
    end,
    
    %% Definiamo l'header CORS
    % Possiamo sostituire "*" con "https://tuosito.com" per maggiore sicurezza
    ACAO = {header, {"Access-Control-Allow-Origin", "*"}},
    
    % Torno gli header per evitare ACAO
    [
      ACAO,
      {content, "application/json", Risultato}
    ]
    .
\end{verbatim} 

Alla funzione vengono passati una serie di parametri inviati dal client. Questi parametri sono passati dentro alla varibile Arg che \`e di tipo record e contiene diversi dati sulla connessione e sulla richiesta inviata al server web. Tra i pi\`u importanti troviamo:

\subsubsection{Dati della Richiesta}
\begin{itemize}
    \item \textbf{Arg\#arg.clidata}: Contiene il corpo (body) della richiesta (es. dati POST o JSON).   
    \item \textbf{Arg\#arg.req}: Contiene un altro record con i dettagli della riga di richiesta HTTP (metodo, percorso, versione).
    \begin{itemize}
        \item \textbf{Arg\#arg.req\#http\_request.method}: L'atomo del metodo (es. 'GET', 'POST').
        \item \textbf{Arg\#arg.req\#http\_request.path}: Il percorso URL (es. {abs\_path, "/index.yaws"}).
    \end{itemize}
    \item \textbf{Arg\#arg.querydata}: Contiene la stringa dei parametri dopo il ? in un URL (es. in test.yaws?id=1, contiene "id=1").
\end{itemize}

I parametri che a noi interessano principalmente sono il metodo di connessioni (GET o POST) perch\'e i dati devono essere prelevati in modo differente, e le due variabili clidata per le chiamate in modalit\`a POST e querydata per le chiamate in modalit\`a GET.

Nel codice sopra possiamo notare una sezione che restituisce degli header aggiuntivi rispetto alla richiesta. Questi header si rendono necessari perch\'e i browser, per evitare che ci possano essere attacchi di tipo XSS (Cross Site Scripting) impediscono collegamenti javascript che siano diretti al di fuori del proprio collegamento.

Nella nostra macchina di test, per poter eseguire contemporaneamente i server http PHP e YAWS abbiamo dovuto differenziare le porte per la connessione. Il server http PHP \`e stato impostato per lavorare sulla porta 80, mentre il server http yaws \`e stato impostato per lavorare sulla porta 8080.
Avendo messo il client sulla porta 80, per il browser qualsiasi collegamento, compresi quelli sulla stessa macchina ma su una porta diversa, vengono visti come collegamenti esterni.

Per ovviare a questo problema \`e necessario che il server conceda, tramite un parametro dell'header la possibilit\`a di accesso da un sito esterno. Per far questo aggiungiamo alla risposta "Access-Control-Allow-Origin" impostando come sito autorizzato a collegarsi "*". Questo significa che tutti i siti esterni sono autorizzati ad accedere al server yaws.

\subsection{Gestione delle diverse tipologie di connessione}
La funzione \textit{processa\_comandi} si occupa di differenziare la gestione dei messaggi in base alla tipologia di connessione.
In questo momento ci concentreremo sui comandi in POST anche se implementeremo comunque anche la gestione di quelli in GET per poter fare dei test di connessione in futuro.

Innanzitutto creeremo una mappa con i parametri da restituire indietro. I parametri principali saranno: title, method, result, risposta. 

I primi due servono principalmente per verificare che la connessione funzioni, in \textit{result} metteremo gli stessi parametri inviati dal client, anche questi per verificare il corretto funzionamento, ed infine in \textit{risposta} ci sar\`a la struttura json con all'interno le informazioni che sono indirizzate al client.

Cercheremo di intercettare eventuali problemi con la gestione dei parametri tramite l'utilizzo delle clausole try ... catch.

La struttura dei dati verr\`a infine convertita in json per essere inviata indietro dal server tramite la funzione \textit{json:encode()}. Utilizziamo la libreria \textit{json} invece di quella proposta nel libro  su Yaws (\textit{rfc4627}) perch\'e quest'ultima necessita di installazione ed \`e obsoleta. Fortunatamente, a partire dalla versione \textit{\textbf{Erlang/OTP 27}} \`e stato integrata direttamente nel linguaggio la libreria json che essendo nativa \`e anche pi\`u veloce e ottimizzata.

\begin{verbatim}
processa_comandi('POST', Arg) ->
    Parametri = #{
        <<"title">> => <<"Arrivato messaggio in POST">>,
        <<"method">> => <<"POST">>,
        <<"result">> => 
            try 
              get_data(Arg)
            catch
              _:_ -> <<"result_error">>
            end,
        <<"risposta">> => 
            try 
              process_data(Arg)
            catch
              _:_ -> <<"process_data_error">>
            end
    },
    Result = json:encode(Parametri),
    Result;

processa_comandi('GET', _Arg) ->
    %equivalente con le mappe di quello fatto fino ad ora
    Parametri = #{
      <<"title">> => <<"Arrivato messaggio in GET">>,
      <<"method">> => <<"GET">>,
      <<"result">> => <<"test_get">>
    },
    Result = json:encode(Parametri),
    Result; 

    processa_comandi(Method, Arg) ->
        Result = io_lib:format("Metodo non gestito: ~p", [Method]),
        Result
    .
\end{verbatim}

\subsection{Memorizzazione dei messaggi}
Per memorizzare i messaggi in transito tra il client e il server, avvenendo la comunicazione in modo asincrono, ci avvarremo del database nativo erlang mnesia \cite{web:mnesia} che ci permetter\`a di memorizzare in modo efficace i vari comandi da inviare al server PHP ed anche le risposte di questo da inviare al client javascript.

Dato che i messaggi inviati dal client e quelli resituiti dal server hanno una struttura simile e che i codici dei messaggi non sono sovrapponibili useremo una sola tabella per la coda dei messaggi.

I record della tabella avranno la seguente struttura:

\begin{table}[h]
	\centering % Centra la tabella nella pagina
	\caption{Struttura dei record della tabella mnesia}
	\begin{tabular}{|c|c|}
		\hline
		\textbf{Nome campo} & \textbf{Significato} \\
		\hline
		id & Identificativo del messaggio \\
		\hline
		msg\_type & Tipo di messaggio \\
		\hline
		payload & Contenuto del messaggio \\
		\hline
		stato & Stato del messaggio (non ancora usato) \\
		\hline
		timestamp & Data e ora di inserimento del dato nel DB (Serve per poter fare pulizia) \\
		\hline
	\end{tabular}
	\label{tab:tabella_mnesia}
\end{table}

Creiamo quindi il codice che permetta di inizializzare il database che dovr\`a contenere la tabella mnesia.

\begin{verbatim}
out(Arg) ->
	Risultato = try
		esegui_inizializzazione()
	catch
		_:Errore -> #{
				<<"result">>  => <<"error">>,
				<<"message">> => list_to_binary(io_lib:format("~p", [Errore]))
			}
	end,
	[
		{header, {"Access-Control-Allow-Origin", "*"}},
		{content, "application/json", json:encode(Risultato)}
	].

esegui_inizializzazione() ->
	Passi = [
		{"schema",  fun crea_schema/0},
		{"mnesia",  fun avvia_mnesia/0},
		{"tabelle", fun crea_tabelle/0}
	],
	Risultati = lists:map(fun({Nome, Funzione}) ->
		Esito = try
			Funzione(),
			<<"ok">>
		catch
			_:Motivo -> list_to_binary(io_lib:format("~p", [Motivo]))
		end,
		{list_to_binary(Nome), Esito}
	end, Passi),
	
	application:set_env(yaws, db_inizializzato, true),
	
	maps:from_list([
		{<<"result">>, <<"ok">>},
		{<<"passi">>,  maps:from_list(Risultati)}
	]).

crea_schema() ->
	case mnesia:create_schema([node()]) of
		ok -> ok;
		{error, {_, {already_exists, _}}} -> already_exists
	end.

avvia_mnesia() ->
	case mnesia:start() of
	ok -> ok;
	{error, {already_started, _}} -> already_started
end.

crea_tabelle() ->
	case mnesia:create_table(richiesta, [
		{attributes, [id, msg_type, payload, stato, timestamp]},
		{type, set},
		%{disc_copies, [node()]}
		{ram_copies, [node()]}
	]) of
		{atomic, ok}                    -> ok;
		{aborted, {already_exists, _}}  -> already_exists
end.
\end{verbatim}

Nel codice erlang del server yaws mettiamo la gestione di scrittura e lettura dei vari messaggi:

\begin{verbatim}
	<<"test_message_m">> ->
		% Salva la richiesta in Mnesia
		Id = inserisci_richiesta(Tipo_Messaggio, Msg_content),
		Parametri_res = #{
			<<"result_type">> => <<"test_result_m">>,
			<<"result_content">> => #{
				<<"result_desc">> => <<Prefisso/binary>>,
				<<"id_message">> => integer_to_binary(Id)
			}
		},
		Parametri_res;
	<<"test_message_r">> ->
		% Leggi la richiesta in Mnesia
		Id = maps:get(<<"Msg_content">>, Parametri, <<"default_value">>),
		case leggi_richiesta(Id) of
		{ok, Result} ->
		Parametri_res = #{
			<<"result_type">> => <<"test_result_r">>,
			<<"result_content">> => #{
				<<"result_desc">> => <<"reading_result">>,
				<<"content">> => integer_to_binary(Id)
			}
		};
		{error, not_found} ->
		Parametri_res = #{
			<<"result">>  => <<"error">>,
			<<"message">> => <<"id non trovato">>
		};
		{error, Reason} ->
		Parametri_res = #{
			<<"result">>  => <<"error">>,
			<<"message">> => list_to_binary(io_lib:format("~p", [Reason]))
		}
		end,
		Parametri_res;
\end{verbatim}

come si pu\`o notare, per poter mantenere la struttura che abbiamo creato per fare i primi test, cambieremo la tipologia dei messaggi che il client dovr\`a inviare al gestore dei messaggi: \textit{\textbf{test\_message\_m}} \`e il messaggio che il client dovr\`a inviare al gestore dei messaggi per effettuare il test, mentre, per controllare lo stato di esecuzione del messaggio useremo \textbf{\textit{test\_message\_r}} che restituir\`a, in caso positivo, l'esito dell'esecuzione.

Il client, se la risposta ricevuta dovesse essere che il messaggio non \`e stato ancora elaborato, attiver\`a di nuovo il timer per controllare lo stato di esecuzione del comando dopo un certo tempo.

\section{Invio dei messaggi da parte del gestore dei messaggi}
L'invio delle richieste dal gestore dei messaggi al server PHP pu\`o avvenire in diversi modi. Quello che utilizzeremo noi in questa prova consiste nel mandare i messaggi in modo sincrono quando un client chiede se la propria richiesta \'e stata processata.

In alternativa la comunicazione potrebbe avvenire attraverso un agente Erlang esterno che processi in modo autonomo. Questa opzione \`e pi\`u complicata da impostare ma \`e in grado di fornire un grado di scalabilit\`a e affidabilit\`a maggiore.

\subsection{Comunicazione sincrona}
Nel nostro caso sfrutteremo il fatto di aver aggiunto, alla tabella del nostro database \textit{mnesia}, lo stato di elaborazione del messaggio. I tre stati che possiamo usare sono: in\_attesa, in elaborazione e completata.
 
Il messaggio, la prima volta che viene inserito nella tabella, avr\`a come valore \textit{\textbf{in\_attesa}} che sta ad indicare che il messaggio non \`e stato ancora processato.

La parte di funzione che si occupa di processare questo \`e il seguente:

\begin{verbatim}
<<"test_message_r">> ->
	% Leggi la richiesta in Mnesia
	Id = maps:get(<<"id">>, Msg_content, 0),
	IdBinary = if
		is_integer(Id) -> integer_to_binary(Id);
		is_binary(Id)  -> Id;
		true           -> <<"id_non_valido">>
	end,
	IdNum = if
		is_integer(Id) -> Id;
		is_binary(Id)  -> binary_to_integer(Id);
		true           -> 0
	end,
	case leggi_richiesta(IdNum) of
		{ok, Result} ->
			Status = element(5, Result), % in_attesa | in_elaborazione | completata
			NewStatus = case Status of
				"in_attesa" -> 
					% non e' ancora stato elaborato il comando
					% cambiamo lo stato in in_elaborazione in modo che al prossimo passo
					% venga inviato al server PHP
					Result_elab = Result,
					binary_to_atom(<<"in_elaborazione">>);
				"in_elaborazione" -> 
					% mi collego al server php per eseguire il comando
					case ConnettiAlServerPHP(Result) of
						{ok, Result_elab} -> 
							binary_to_atom(<<"completata">>);
						{busy, _} -> 
							Result_elab = Result,
							binary_to_atom(<<"in_elaborazione">>);
					end;
				"completata" -> 
					Result_elab = Result,
					binary_to_atom(<<"in_elaborazione">>)
			end,
			case aggiorna_stato(Id, NewStatus) of
				{atomic, ok} ->
					ok;
				{aborted, Reason} ->
					{error, Reason}
			end,
	Parametri_res = #{
		<<"result_type">> => <<"test_result_r">>,
		<<"result_content">> => #{
			<<"result_desc">> => <<"reading_result">>,
			<<"content">> => record_to_map(Result_elab)
		}
	};
	
\end{verbatim}

Quando il client ci chiede se ci sono risposte alla sua richiesta, nel nostro caso \textbf{\textit{test\_message}}, andiamo a leggere lo stato corrispondente alla richiesta con identificativo \textit{\textbf{Id}}.

Se lo status era \textit{in\_attesa} lo cambiamo con \textit{in\_elaborazione}.
La volta successiva che il client ci far\`a la richiesta di conoscere il risultato dell'elaborazione invieremo il contenuto del messaggio al server PHP che, nel caso in cui riesca ad elaborarla la segner\`a come \textit{\textbf{completata}} nella tabella delle richieste.

Il client, nella iterazione successiva, trovando che quel particolare Id \`e stato completato chieder\`a al gestore dei messaggi di cancellarlo. 

\subsubsection{Invio di dati da erlang al server PHP}
 Per spedire i dati al server useremo, come visto, la funzione \textbf{\textit{send\_http\_request}} che, dato il json da inviare al server, ci restituir\`a il risultato dell'elaborazione o il fatto che il server \`e sovraccarico.
 
 Per l'invio utilizzeremo le funzioni native di Erlang per la comunicazione e in particolare \textbf{\textit{httpc:request(}}.

\begin{verbatim}
	send_http_request(JsonBody) ->
	% Ci assicuriamo che inets sia avviato
	application:ensure_all_started(inets),
	application:ensure_all_started(ssl),
	
	
	% Content-Type deve essere application/json
	ContentType = "application/json; charset=utf-8",
	Url = "http://localhost/server.php",
	
	case httpc:request(post,
	{Url, [], ContentType, JsonBody},
	[{timeout, 5000}],
	[]) of
		{ok, {{_, StatusCode, _}, _Headers, ResponseBody}} ->
			DecodedResponse = json:decode(iolist_to_binary(ResponseBody)),
			JsonBodyReturn = #{
				<<"Status">> => integer_to_binary(StatusCode),
					<<"Risposta">> => DecodedResponse
				},
				% qui va controllato se il server era troppo occupato
				{ok, JsonBodyReturn};
			{error, Reason} ->
				io:format("Errore: ~p", [Reason])
	end
	.		
\end{verbatim} 

\subsection{Comunicazione asincrona}
Una soluzione migliore \`e quella di avere un modulo esterno in Erlang che venga inizializzato e che si occupi, in modo autonomo, di pescare dalla tabella mnesia e di fare la chiamata al server PHP mettendo il risultato, nel caso in cui la connessione vada a buon fine, dentro il database per poter essere recuperato dal client.

Il problema di questa soluzione \`e che Yaws, in configurazione standard, avvia una propria VM Erlang che \`e diversa e isolata da quella installata sulla macchina virtuale.
Per risolvere il problema dobbiamo collegare le due VM in modo che possano condividere anche le tabelle mnesia.
Questo \`e possibile cambiando il file di configurazione di Yaws in modo che la macchina virtuale venga lanciata con il nome e con lo stesso cookie che useremo per la VM di Erlang in modo che possano condividere la stessa rete:

Ad esempio:
\begin{verbatim}
# Avvio VM 1 (app che si collega con server PHP)
erl -name app@localhost -setcookie mio_cookie_segreto

# Avvio Yaws con lo stesso cookie
yaws --erlarg "-name yaws@localhost -setcookie mio_cookie_segreto"
\end{verbatim}

ora che sono nella stessa rete le due VM vanno connesse:

Dalla VM della app, ci connettiamo a Yaws e verifichiamo che siano connessi
\begin{verbatim}
1> net_kernel:connect_node('yaws@localhost').

2> nodes().
% -> ['yaws@localhost']

\end{verbatim}

e infine va collegato il database mnesia

\begin{verbatim}
% Dal nodo ESISTENTE (quello con il DB)
mnesia:change_config(extra_db_nodes, ['nuovo@localhost']).
\end{verbatim}

Il problema di questa soluzione \`e che, per funzionare, Yaws deve essere configurato in modo che possa comunicare con altri worker di erlang.
Questo pu\`o essere fatto in diversi modi:

1. Script di avvio (modo pi\`u comune)
\begin{verbatim}
# /etc/yaws/yaws.start oppure in uno script
yaws --erlarg "-name yaws@localhost -setcookie mio\_cookie"
\end{verbatim}

2. File yaws.conf - parametro erl\_flags

\begin{verbatim}
	conferl_flags = -name yaws@localhost -setcookie mio_cookie
\end{verbatim}
 
3. File /etc/yaws/yaws.conf - sezione globale
\begin{verbatim}
# Sezione globale in cima al file
logdir = /var/log/yaws
ebin_dir = /usr/lib/yaws/ebin

# Parametri erlang
erl_flags = -name yaws@localhost -setcookie mio_cookie
\end{verbatim}

4. Variabile d'ambiente
\begin{verbatim}
export ERL_FLAGS="-name yaws@localhost -setcookie mio_cookie"
yaws --daemon
\end{verbatim}

I due server, dato che hanno in condivisione anche il server mnesia non hanno bisogno di comunicare tra di loro con la messaggistica integrata di Erlang.
 

\section{Comunicazione tra gestore dei messaggi e server PHP}

\subsection{Limitazione del numero di connessioni al server PHP}
Ci sono diversi metodi per limitare il numero connessioni che il server PHP accetta dal gestore dei messaggi. Alcuni dei pi\`u comuni sono:
\begin{itemize}
    \item Webhooks semplice (Push asincrono via HTTP)
    \item Semaphore (Semafori a livello di Sistema Operativo) 
    \item Gestione tramite il Web Server (Nginx / PHP-FPM)
    \item Usare una tabella del database per gestire il numero di processi
\end{itemize}

Ognuno di questi ha dei vantaggi e degli svantaggi. Webhooks ad esempio ha il vantaggio che \`e il gestore dei messaggi ad inviare i messaggi ma rimane con lo stesso problema che abbiamo con la configurazione originale client/server; rischiamo infatti che il server di sovraccarichi.
Semaphore d'altro canto richiede, per l'utilizzo dei semafori del sistema operativo, che il nostro web server si trovi su un distribuzione Linux.
La gestione del numero massimo di processi modificando la configurazione del web server richiede invece la possibilit\`a di modificare i file di configurazione, cosa che non sempre \`e possibile e che dipende dalla scelta della macchina su cui far girare i nostri sorgenti PHP. Potrebbe essere una configurazione condivisa senza possibilit\`a di cambiare i parametri di base.

L'utilizzo di una tabella del nostro database mysql o mariadb per gestire il numero massimo di richieste in arrivo dal gestore dei messaggi sembra quindi essere la soluzione migliore.
Non siamo legati al sistema operativo e non abbiamo bisogno di accedere alla configurazione di PHP. Il database \`e gi\`a installato per memorizzare i risultati delle prove svolte.

\subsubsection{Implementazione del codice per limitare le connessioni}
Come gi\`a detto, per limitare le connessioni al server web PHP, implementeremo una gestione apposita. 

Nel momento arriva una nuova connessione andremo a vedere, nella tabella delle connessioni attive, quante connessioni sono gi\`a in essere. Se il numero supera il numero massimo stabilito risponderemo alla chiamata con un messaggio che indichi il sovraccarico. In caso contrario aggiungeremo alla tabella un elemento ed eseguiremo il comando che ci \`e stato richiesto. Al termine del comando cancelleremo dalla tabella la riga corrispondente.

Potrebbe per\`o capitare che, per errori nel codice PHP o altro, l'esecuzione si interrompa in modo inaspettato lasciando nella tabella una riga non pi\`u valida. L'accumulo di queste righe impedir\`a la ricezione di nuovi messaggi da parte del gestore dei messaggi. Implementeremo quindi una procedura di emergenza che, ad intervalli casuali di tempo, cancelli gli elementi della tabella pi\`u vecchi. Possiamo stabilire, come tempo massimo di permanenza nella tabella, un minuto. Sar\`a infatti molto improbabile che ci siano processi che richiedano pi\`u id una trentina di secondi per essere eseguiti. 

Creiamo quindi la tabella nel database:

  $stmt = $db->prepare("INSERT INTO processi_attivi (token_univoco) VALUES (?)");

  return $mio_id;   
}
